## 1. 当前需要冻结的核心结论

### 1.1 硬件与安装

| 项目 | 当前结论 | 证据等级 | 主要来源 |
|---|---|---:|---|
| 雷达 | POSSUMIC RS6240 / MRS6240-P2512 | A | RS6240 Datasheet；正式采集程序 |
| 天线 | 2Tx × 4Rx，AiP | A | RS6240 Datasheet |
| 安装方式 | **竖装**，雷达正对胸骨上段，约 0.4 m | A/B | 实验安装确认；FocusWave README |
| RX 间距 | 方位与俯仰方向均为 **2.45 mm** | A | `RS6240_Datasheet_V1.4_EN.pdf`，5.1 Antenna Configuration |
| SDK 阵列类型 | `MMW_ANT_GEOMETRY_A43` | A | SDK V2.1.1 `mmw_alg_doa.h` |
| 竖装官方方位子阵列 | 虚拟通道 `{0,1,4,5}` | A | SDK V2.1.1 `mmw_app_pointcloud.c::set_ant_geometry()` |
| 竖装官方俯仰子阵列 | 虚拟通道 `{3,2,1}` | A | SDK V2.1.1 `mmw_app_pointcloud.c::set_ant_geometry()` |

```text
[tx0_ant0, tx0_ant1, ... tx1_ant0, tx1_ant1, ...]
```

因此对 2T4R，当前应按下列顺序理解：

```text
0 = tx0_rx0
1 = tx0_rx1
2 = tx0_rx2
3 = tx0_rx3
4 = tx1_rx0
5 = tx1_rx1
6 = tx1_rx2
7 = tx1_rx3
```

来源：SDK V2.1.1 `mmw_alg_pointcloud.h`。Codex 必须再与 FocusWave 实际 NPZ key 排序逻辑核对一次，禁止只凭命名假设数组轴顺序。

### 2.2 不能冻结为已知的参数

以下目前仍是**未解决项**：

1. `Tx0/Tx1` 的真实 TDM/chirp 发射顺序；
2. `Tx0 -> Tx1` 的精确时间间隔；
3. FocusWave PSIC header 中的 `interval_us=57` 是否恰好等于正式固件真实值；
4. `ReportDataCube1D` 输出到主机前，RS6240 的 8 路数据是否已经执行官方 antenna gain/phase calibration；
5. 若执行 calibration，使用的是哪组 NVM coefficient、何时写入、正式实验板卡是否保持同一组 calibration。

特别注意：FocusWave 当前代码对 `interval_us=57` 的注释是 **“SDK demo 默认”**，不是“已从正式固件确认”。因此不得把 57 µs 写成正式实验已证实参数。

## 3. 数据域定义：禁止再混淆 raw ADC 与 range cube

FocusWave 当前正式数据应描述为：

> **8-channel complex range-bin data / 8 通道复数距离域数据**

概念结构：

```text
Z[frame, range_bin, virtual_channel] ∈ C
≈ frame × 256 × 8
```

它不是普通意义的 raw fast-time ADC：

```text
raw ADC fast-time
  -> 固件/雷达框架内部处理
  -> 1D complex range-domain DataCube
  -> ReportDataCube1D
  -> FocusWave DatacubeConversion
  -> NPZ: tx*_rx* complex arrays
```

因此：

- 当前主线不应再次对这批正式 NPZ 做 Range FFT；
- 旧脚本若把 NPZ 当 raw ADC 再 FFT，应继续保留为历史/错误语义，不得重新引入主线；
- Codex 需要再次核验 `scripts/process_vital_signs_v3_1_1.py` 的 range-cube 入口逻辑，以及正式主分析实际调用链。

来源：

- `kyandi233-dev/FocusWave` `stable-msmf`：`01-MainProgram/core/mmwave_capture.py`
- `greenboo26/mmwave-hrv-analysis`：`scripts/process_vital_signs_v3_1_1.py`

## 4. RS6240 官方 SDK 对 8 通道的处理证据

### 4.1 官方并不把 8 路裸平均

SDK V2.1.1 PointCloud/DoA 链明确区分：

1. **全部 MIMO 通道的非相干功率汇总**：用于功率/检测；
2. **天线 gain/phase calibration**；
3. **按阵列 geometry 选择阵元子集**；
4. 再做 angle processing。

`mmw_alg_pointcloud.h` 明确说明 power 可按 all antennas 做 non-coherent sum。

### 4.2 RS6240 官方 calibration

SDK 明确写：

```text
Channel calibration should be manually done for all mimo_rx
```

且校准运算形式为：

```text
ant_output_data = ant_input_data .* ant_calibrate_data
```

来源：

- `mmw_alg_doa.h`
- `mmw_alg_pointcloud.h`
- `mmw_app_pointcloud.c`

Factory Test `ft_angle_est.c` 进一步说明：

```text
for 624x, phase align at Rx0
```

并提供 2T4R calibration coefficient 的 NVM 读取路径（`HWINFO_ID_NVM_ANT_CALIB_2T4R`）。

### 4.3 重要边界

**固件镜像里出现 `MIMO Calib Load` 字符串，不等于正式 `ReportDataCube1D` 输出已经完成 calibration。**

原因：同一镜像可以链接 radar framework、factory test、point cloud 等多个模块。必须检查**实际 1D 运行路径**，或者通过数据做结果层面的相干性/相对相位验证。

因此当前禁止写：

> “正式 NPZ 已经经过官方天线校准。”

正确表述只能是：

> “正式镜像包含 RS6240 MIMO calibration 相关实现，但 ReportDataCube1D 输出路径是否实际应用该 calibration 尚未确认。”

## 5. 当前算法对 8 路的实际使用方式

当前主线 `scripts/process_vital_signs_v3_1_1.py` 明确：

```python
FS = 100.0
N_CH = 8
```

当前已知管线属于：

```text
8 路候选搜索
  -> 为 BR/HR 选择较优 channel + range bin
  -> 最终波形从一个选中的 channel/bin 提取 phase
```

因此现状应描述为：

> **multi-channel candidate search / best-channel selection**

而不是：

> 8-channel fusion / MIMO beamforming。

下一轮不得直接替换现有 baseline。所有新融合算法必须作为 ablation/experimental branch 与当前 best-channel 进行同数据比较。

---

## 6. 已知 HRV 风险：多通道融合不能只看 SNR

项目已有 ECG/RSP 金标准审计发现：当前最严重风险是**呼吸二/三次谐波落入 cardiac band，形成“强而错”的心搏候选**。

所以多通道算法不能用：

```text
8 路更一致 / SNR 更高
```

直接推出：

```text
heartbeat 更正确 / HRV 更可靠
```

因为 8 路也可能一致地增强同一个呼吸谐波。

最终判定必须落在 ECG beat-to-beat 层面。

## P1 — 用现有正式/校准数据做 8 通道可融合性审计

新增建议脚本：

```text
scripts/audit_rs6240_multichannel.py
```

只读原始数据，不修改现有输出。

### P1.1 数据完整性

对优先选取的 ECG/RSP 校准场次 + 若干正式静息/任务场次检查：

- NPZ 是否稳定存在 8 个 `tx*_rx*` key；
- 每路 shape 是否一致；
- key -> channel index 映射；
- 实际 timestamp 行数；
- `(N-1)/(t_last-t_first)` 有效采样率；
- frame gap / jitter / dropped-frame metrics。

### P1.2 8×8 通道关系

在当前可信胸部 range bin（并做小范围邻域敏感性）计算：

1. complex magnitude power；
2. unwrapped phase；
3. phase increment `Δφ`；
4. phase-jump rate；
5. pairwise correlation；
6. magnitude-squared coherence；
7. 相对复数比 `z_c / z_ref` 的幅度与相位稳定性。

至少分别输出：

```text
all-band
BR band: 0.1–0.5 Hz
cardiac band: 与当前主线一致（先核当前实际范围）
```

比较组：

```text
TX0: {0,1,2,3}
TX1: {4,5,6,7}
cross-TX
vertical azimuth geometry: {0,1,4,5}
vertical elevation geometry: {3,2,1}
```

### P1.3 判定重点

若出现：

```text
同 Tx 内相干性高，跨 Tx 明显下降
```

则优先允许 same-Tx 4Rx phase-domain fusion，暂缓 8ch complex coherent fusion。

若 8 路在 cardiac band 相干很高，也必须继续与 ECG 检查，避免只是共同锁定呼吸谐波。

### P1.4 输出

```text
output/10_质量控制/RS6240_8ch可融合性审计_v1/
  channel_mapping.csv
  timestamp_quality.csv
  channel_quality.csv
  pairwise_corr.csv
  pairwise_coherence_br.csv
  pairwise_coherence_hr.csv
  relative_phase_stability.csv
  figures/
  audit_summary.json
```

批量原始波形不进入 Git；只提交小型审计汇总/方法文档。

2. 其次用现有静息/校准人体数据做结果层推断；

## P3 — 多通道融合 ablation（先 phase-domain，后 complex-domain）

新增独立模块，建议：

```text
scripts/multichannel_fusion.py
scripts/evaluate_multichannel_fusion_ecg.py
```

**不得覆盖 `process_vital_signs_v3_1_1.py` 当前 baseline。**

### P3.1 必须保留的模型

| ID | 方法 |
|---|---|
| S1 | 当前 best single channel/bin baseline |
| T0 | TX0 `{0,1,2,3}` phase-domain weighted fusion |
| T1 | TX1 `{4,5,6,7}` phase-domain weighted fusion |
| A4 | 竖装官方方位子阵列 `{0,1,4,5}` phase-domain fusion |
| C8-PH | 全 8 路 phase-domain weighted fusion |
| P8 | 8 路 non-coherent power，仅用于 range/quality，不作为 heartbeat 波形 |

第一阶段使用：

```text
unwrap(angle(z_c))
-> center 或 phase increment
-> channel QC
-> correlation/coherence gating
-> weighted fusion
```

第一阶段**不要**直接：

```text
sum(z_0 ... z_7)
```

### P3.2 Complex coherent fusion 的进入条件

只有同时满足：

1. exact source 或实验确认 calibration 状态；
2. 跨 Tx 相对相位在目标数据中足够稳定；
3. Tx/chirp timing 不构成不可忽略的系统误差，或已实现正确补偿；
4. ECG 验证显示优于 phase-domain/best-channel；

才增加：

```text
C8-CX = calibrated/phase-aligned complex coherent fusion
```

### P3.3 Beamforming 的进入条件

Bartlett/Capon/MVDR/AoA 暂列后续 M3，不作为当前 P0–P3 首要任务。

原因：当前正式场景为单人、正面、约 0.4 m；首先需要证明 channel diversity 对 heartbeat/IBI 有实益。若 phase-domain/complex fusion 无收益，不应因 2T4R 硬件存在就强行引入 beamforming。

同时，当前 1D 正式数据不能重新宣称可靠头姿角输出；项目既有实测已经记录跨通道逐帧测角不稳定。

## P4 — ECG 逐搏验证：最终决策标准

所有 fusion 模型必须在**相同场次、相同时间窗口、相同 ECG 清洗标准**上比较。

最低指标：

```text
beat detection recall
false beat rate / precision
matched beat timing error
IBI MAE
IBI RMSE
HR MAE
RMSSD bias / MAE
SDNN（仅在时长与方法学允许时，避免把 30s 窗当长期 HRV）
respiratory-harmonic mis-lock rate
usable-window rate
```

必须重点报告：

> 多通道是否降低“强而错”的呼吸谐波锁定，而不仅是提高 SNR。

权重/QC 参数不得使用测试 ECG 标签进行调优；沿用已有独立留出/LOSO 原则，避免数据泄漏。

---

## P5 — 决策门

### 允许进入主线候选

若某融合模型相对 S1：

- IBI MAE/RMSE 有稳定改善；
- heartbeat recall 提升且 false beat 不恶化；
- respiratory-harmonic mis-lock rate 不增加；
- 改善跨校准场次/被试重复出现；

则标记为 `candidate_for_mainline`，再讨论主线升级。

### 不允许进入主线

以下任一情况成立：

- 只提高频谱 SNR，但 ECG IBI 不改善；
- 8 路更一致但实际共同增强呼吸谐波；
- 仅个别场次改善；
- complex fusion 对未知 calibration/timing 高敏感；
- 需要 ECG 标签才能选权重；

则保持 experimental，不替换当前 baseline。
