# GPT↔Codex 双边协作协议

## 目的

为 GPT 与 Codex 之间提供单一、可追溯、低体积、**优先复用既有成果**的协作方式。

本协议新增一条最高优先级规则：

> `docs/WORKSPACE_LEDGER.md` 是项目唯一长期总账。任何新任务开始前必须先读总账；任务结束后必须更新总账。不得只依赖聊天记录或单次 handoff 判断“之前做没做过”。

---

## 1. 三层信息结构

### A. 本地 worktree / 本地数据

这是 Codex 真正运行代码、访问 D 盘数据、产生被试级和大型派生文件的地方。

GitHub 不上传原始数据和被试级数据，不代表这些文件不存在。

### B. `docs/WORKSPACE_LEDGER.md`

这是**长期项目总账**，记录：

- 本地 worktree 路径；
- 关键本地产物的完整路径和文件名；
- 哪些资产已经完成、可以复用；
- 哪个文件是当前权威版本；
- 当前真正未完成什么；
- 当前最多三条活跃主线。

GPT 每次先读总账，不再从大量旧 handoff 中自行拼接项目状态。

### C. 单次 handoff / adjudication

用于记录某一轮具体任务的结果和裁决，不承担长期资产索引职责。

---

## 2. Codex 开始任何任务前的强制检查

每次任务开始前，Codex 必须先读取 `docs/WORKSPACE_LEDGER.md`，并在运行记录中明确回答：

1. 这个问题之前是否已经做过？
2. 有哪些本地旧产物可以直接复用？请给出完整路径和文件名。
3. 本次是“复用/连接旧资产”还是“重新计算”？
4. 如果要重做，旧资产为什么不能用？

**如果总账中已经存在可复用资产，默认禁止从零重做。**

不得因为 GitHub 没有上传被试级表，就把状态误判为“identity 未恢复”或“结果不存在”。

---

## 3. Codex 交接要求

每次交接只提交一份 Markdown 汇总文件，建议路径：

`docs/decisions/YYYY-MM-DD-<topic>-handoff.md`

文件必须包含：

- `RUN_ID`、日期、当前分支和 commit；
- 本地 worktree 根目录；
- 输入范围；
- **复用的旧资产：完整本地路径 + 文件名 + 用途**；
- 新产物：完整本地路径 + 文件名；
- 已执行入口、配置和数据划分规则；
- 关键结果与样本覆盖；
- `formal / exploratory / blocked / unverified` 状态；
- 失败原因、限制和未解决风险；
- 是否替代旧资产；
- 请求 GPT 裁决的问题；
- 下一步只写最直接的一步。

如果本次没有产生新的科研结果、没有新增可复用资产、也没有解除关键 blocker，必须显式标记：

`NO_NEW_SCIENTIFIC_OUTPUT`

避免用“完成了审计”掩盖没有实质进展。

---

## 4. Codex 结束任务后的强制更新

每次 handoff 提交前，必须同步更新：

`docs/WORKSPACE_LEDGER.md`

至少更新：

- 做了什么；
- 复用了什么旧文件；
- 新产出了什么具体文件；
- 当前权威资产；
- 是否有旧资产被替代；
- 当前状态；
- 下一步；
- commit。

关键本地资产不得只记录到目录层级。必须尽可能写到具体文件，例如：

`D:\...\participant_session_crosswalk.csv`

并记录关键字段、行数和生成来源。

---

## 5. GitHub 上传边界

允许提交：

- 脚本；
- 配置示例；
- 方法文档；
- 聚合结果；
- 运行清单；
- 审计摘要；
- 总账；
- GPT 裁决。

禁止提交：

- 原始数据；
- 被试级 CSV；
- 视频；
- NPZ；
- MAT；
- 大型派生文件；
- 个人身份信息；
- 凭据；
- 缓存和运行时数据库。

对于禁止上传但后续必须复用的本地文件，只在总账记录：

- 完整本地路径；
- 文件用途；
- 行数/字段；
- RUN_ID；
- 当前状态。

---

## 6. GPT 读取和裁决要求

GPT 固定按以下顺序工作：

1. 先读 `docs/WORKSPACE_LEDGER.md`；
2. 再读当前活跃主线明确引用的 handoff；
3. 只有确实需要时才读旧决策或方法文件；
4. 在提出新 blocker/gate 前，先检查总账是否已有旧资产解决该问题；
5. 若只是“旧资产未被新任务读取”，优先要求复用，不得重新立项。

GPT 裁决必须区分：

- 可以进入正式分析；
- 仅可作为探索性结果；
- 当前阻塞；
- 尚未验证。

GPT 不应在证据不足时改变标签、阈值、数据划分或主要科学解释，也不应为了形式完美不断新增审计门槛。

---

## 7. 当前任务数量限制

同时 active 的主线最多 3 条。

每条主线必须包含：

- 目标；
- 已有输入；
- 本次必须产生的输出；
- 状态；
- 下一步。

没有明确输出的“继续调查”“再核验一下”不能成为主线。

---

## 8. 面向用户的表达规则

优先使用普通中文，不用一串英文标签代替实际意思。

例如：

- `crosswalk` → 被试/session 对照表；
- `semantic gate` → 标签含义和程序版本确认；
- `participant-disjoint` → 同一个人不能同时出现在训练集和测试集；
- `provenance` → 结果/文件从哪里来、能不能追溯；
- `worktree` → 本地正在工作的代码文件夹。

必须使用专业英文缩写时，第一次先给中文含义。

---

## 9. 用户如何判断进展

以后不以 commit 数、Markdown 数、审计数作为主要进度。

只有以下三类才算实质进展：

1. 新科研结果：图、统计结果、模型比较、生理验证；
2. 新可复用资产：身份表、时间线、共同样本表、确定的数据映射；
3. 清除关键 blocker：原来不能分析，现在可以正式分析。

如果一天主要增加的是 handoff 和 PASS/BLOCKED 表，没有上述三类之一，应明确告诉用户“今天实质科研进展有限”。

---

## 10. 推荐交接提示词

> 先读取 `docs/WORKSPACE_LEDGER.md`，确认已有本地产物和当前权威资产，禁止重复恢复已经存在的身份、时间线、标签或共同样本。然后读取当前 handoff。执行前说明本次复用了哪些具体本地文件；执行后更新总账，并提交一份轻量 handoff。若没有产生新科研结果、新可复用资产或解除 blocker，请明确标记 `NO_NEW_SCIENTIFIC_OUTPUT`。
